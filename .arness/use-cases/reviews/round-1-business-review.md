## Per-Use-Case Feedback

**UC-001: Compile Current Reading List**
- **[Minor]:** The filename convention `wharfinger-courier-<YYYY-MM-DD>.xhtml` (step 7, also BR in UC-006) does not address the case where Nik runs the tool twice in one day. The second run would overwrite the first document silently. --> Add a business rule specifying the overwrite policy explicitly: either the second run overwrites intentionally (document is cumulative or replaces), or the filename includes a sequence suffix to prevent data loss. Given the "Resilient and resumable runs" pillar, silent data loss should be addressed.
- **[Minor]:** Extension 5d classifies "all articles fail" as "partial success" but the postcondition section only describes the full success case in detail. --> Clarify what the minimal guarantee looks like when status.json is updated (step 8 still runs per 5d.3) but no document is produced. The current text says "No partial status.json is written" under minimal guarantee, which could be read as contradicting 5d.3 where status.json IS updated with failure statuses.
- **[Minor]:** Extension 7a (output directory not writable) says status.json is not updated with document metadata, but does not say whether per-article statuses (EXTRACTED) are preserved in status.json. --> Clarify: if articles were successfully extracted in step 5 but the document write fails, are those EXTRACTED statuses persisted? If not, the next run would redundantly re-extract cached content. If yes, the status.json write in step 8 needs to distinguish document metadata from article statuses.

**UC-002: Compile Archive Reading List**
- **[Critical]:** The product concept says `courier --since N` where N is "a number of days," but there is no business rule specifying what value of N is valid. Can N be zero? Can it be 365? Is there a practical upper bound? --> Add a business rule defining the valid range for N, or at minimum state that N must be a positive integer. Consider whether an unreasonably large N (e.g., 3650) should be capped or warned about, since the Pinboard feed itself may only return a limited number of bookmarks.
- **[Minor]:** The relationship between UC-002 and UC-001 is modelled as "extends," but UC-002 has its own complete main success scenario that duplicates nearly all of UC-001. This is a modelling concern, not a business gap, but it creates a maintenance risk: if a business rule changes in UC-001 (e.g., the article cap default), UC-002 must be updated independently. --> Consider whether UC-002's business rules should explicitly reference UC-001's rules by number where they are identical, to make the dependency visible.
- **[Minor]:** The `--since` flag semantics are ambiguous regarding time-of-day. "Within the last N days" could mean last N calendar days or last N*24 hours. --> Add a business rule specifying whether the N-day window is calendar-based (midnight to midnight) or rolling (current time minus N*24 hours).

**UC-003: Configure the Tool for First Use**
- **[Critical]:** The trigger says "Nik runs the tool for the first time (or any time no status.json exists in the expected location)." This conflates two different situations: first-time configuration and a missing status.json after prior use (which could indicate accidental deletion or a moved state directory). Configuration validation should happen on every run (the config file must be valid), but the trigger implies this use case only fires when status.json is absent. --> Separate the trigger: UC-003 covers creating the config file and initial validation. Config validation on subsequent runs should either be folded into UC-001's precondition check or noted as a standing precondition that runs silently. The status.json trigger is misleading since status.json absence is handled as an extension in UC-001 step 2a.
- **[Minor]:** Step 7 performs a test HTTP GET to the Pinboard feed URL during configuration. This is a network call that could fail for transient reasons (Pinboard temporarily down) even though the config is correct. A first-time user who sets up config while offline would be blocked. --> Consider making the feed reachability check a warning rather than a fatal error during configuration. The "No infrastructure ceremony" pillar suggests setup should be low-friction.
- **[Minor]:** The product concept mentions "environment variables" as an alternative to a config file, but UC-003 only describes the TOML file path. --> Either add environment variable support as an alternate flow in UC-003, or note in the product concept that environment variables were deferred. Current inconsistency between the two documents may cause confusion during implementation.

**UC-004: Fetch Bookmark Feed**
- **[Minor]:** The use case returns two sets: "new bookmarks" and "all bookmarks." UC-001 only needs uncompiled bookmarks (which may differ from "new" -- an article could be known but in FETCH_FAILED state, which is not new but is uncompiled). UC-002 needs all bookmarks within a date range. The partitioning logic here does not clearly serve either caller's actual need. --> Clarify the contract: "new" means "URL not in status.json" but UC-001 also needs to process known articles that are not yet COMPILED (e.g., previously failed). The orchestrator presumably handles this filtering, but the two-set return from UC-004 implies UC-004 is doing meaningful partitioning. Either UC-004 should return just the raw feed and let the orchestrator filter entirely, or the partition logic should match what callers actually need.
- **[Minor]:** No business rule addresses rate limiting or politeness toward the Pinboard API. While the product concept notes the feed is a public URL, repeated rapid invocations could hit rate limits. --> Consider adding a note that the feed is fetched at most once per invocation (already stated) and that no caching of the feed response between runs is performed. If Pinboard ever introduces rate limiting, this would be the use case to amend.

**UC-005: Fetch and Extract Article**
- **[Minor]:** The minimum word-count threshold is referenced as a precondition ("minimum word-count threshold is configured") but is not listed as a configuration field in UC-003. --> Add `min_word_count` (or equivalent) to UC-003's configuration fields, either as a required field or as an optional field with a documented default.
- **[Minor]:** The HTTP timeout is listed as a precondition ("HTTP timeout ... configured") but is similarly absent from UC-003's configuration fields. --> Add `http_timeout` to UC-003's configuration fields with a default value.
- **[Minor]:** There is no business rule about what content types are acceptable. If the article URL returns a PDF, an image, or a non-HTML content type, the extraction step would likely fail in an undefined way. --> Add a business rule: the system checks the response Content-Type and only proceeds with extraction for HTML content types. Non-HTML responses should result in a defined status (e.g., UNSUPPORTED_CONTENT_TYPE) rather than an unpredictable extraction failure.

**UC-006: Compile Kindle Document**
- **[Minor]:** Extension 1a (archive mode) says "also includes articles with status COMPILED that fall within the archive date range" but does not specify where the date range comes from. The orchestrator passes it, but this is the only place in the use case set where UC-006 needs to know about the archive date range. --> Clarify the interface: does UC-006 receive a pre-filtered list of articles from the orchestrator, or does it independently query status.json with a date range? The former is cleaner and keeps UC-006 unaware of selection policy. If so, rewrite 1a to say "The orchestrator passes a combined list including previously compiled articles; UC-006 processes whatever list it receives."
- **[Minor]:** No business rule addresses what happens if the output file already exists (same date, second run). This is the same concern raised for UC-001 but is specifically UC-006's responsibility since it writes the file. --> Add a business rule: the system overwrites any existing file with the same name, or appends a suffix. State the policy explicitly.

**UC-007: Preview Run Without Changes**
- **[Minor]:** BR-5 says selection logic matches UC-001, but there is no equivalent `--dry-run --since N` mode that would preview an archive run (UC-002). If Nik wants to preview what an archive run would include, there is no mechanism for it. --> Either add a note that `--dry-run --since N` is out of scope for v1, or extend UC-007 to accept the `--since` flag in combination with `--dry-run`. Given UC-007 is Should-have and UC-002 is Should-have, this is not urgent, but the gap should be acknowledged.
- **[Minor]:** The dry-run fetches the Pinboard feed (a network call) but the postcondition says "No files have been written, modified, or created." This is correct but the phrasing could mislead someone into thinking dry-run is fully offline. --> Consider adding a note to the postconditions or business rules: "The Pinboard feed is fetched over the network; dry-run is not an offline mode."

## Cross-Cutting Observations

- **Missing use case:** There is no use case for inspecting or managing the status.json state. The product concept mentions that articles can be PERMANENTLY_SKIPPED after 10 failed attempts, but there is no mechanism for Nik to review which articles have been skipped, reset a skipped article, or clear stale state. This matters because the "Resilient and resumable runs" pillar depends on status.json being correct, and over time it will accumulate entries for bookmarks Nik no longer cares about. A simple `courier status` command showing counts by state and listing permanently skipped URLs would serve this need. Priority: Could-have for v1, but the gap should be noted.
- **Missing use case:** There is no use case covering what happens when Nik removes a bookmark from Pinboard (or marks it as read on Pinboard). Currently, status.json will retain entries for articles that no longer appear in the feed. This is benign for storage but means status.json grows unboundedly over time. A business rule about whether stale entries are ever pruned would clarify long-term state management.
- **Missing configuration fields:** UC-005 references `min_word_count` and `http_timeout` as preconditions, but UC-003 does not list them as configuration fields. This is a consistency gap across the use case set. Any configuration parameter that affects business behaviour should be traceable back to UC-003.
- **Consistency issue:** The product concept's "First-Time Setup" section mentions "environment variables" as an alternative to a settings file, but UC-003 only describes the TOML config file. This inconsistency should be resolved -- either add environment variable support to UC-003 or update the product concept to remove the mention.
- **Consistency issue:** UC-004 returns "new bookmarks" and "all bookmarks" but neither UC-001 nor UC-002 uses exactly this partitioning. UC-001 needs "uncompiled bookmarks" (which includes previously failed articles, not just new ones). UC-002 needs "all bookmarks within date range." The abstraction in UC-004 does not cleanly match its callers' needs, which could cause confusion during implementation.
- **Scope concern:** The filename collision issue (two runs on the same day) touches UC-001, UC-002, and UC-006 but is not addressed by any of them. This needs a single authoritative business rule, most naturally in UC-006 since that is where the file is written, with UC-001 and UC-002 deferring to it.
- **Scope concern:** No use case addresses cache disk usage over time. The cache directory will grow with every new article fetched. For a personal tool this is unlikely to be urgent, but a note acknowledging that cache pruning is out of scope for v1 would be useful to prevent scope creep during implementation.
