## Spike 001: Extraction Quality, XHTML Sanitisation, and Title Quality

### Risk Description

Three linked risks validated together (as recommended by the architecture vision):
1. `readability-lxml` may underperform on Nik's specific bookmark diet (personal blogs, academic papers, forums, paywalled sites)
2. `lxml.html.tostring(method="xml")` may not sanitise all extracted HTML to valid XHTML (malformed entities, unusual Unicode, unclosed void elements)
3. `readability-lxml`'s `doc.title()` may return generic strings ("Home", "Untitled") on some sites

### Priority

Critical — the architecture vision explicitly requires validating extraction quality on real bookmarks before building the pipeline.

### Validation Criteria

- [x] ≥80% of articles extract meaningful body content (navbars/ads stripped; article body present)
- [x] `lxml.html.tostring(method="xml")` produces well-formed XHTML for all fetched articles
- [x] `doc.title()` returns a useful title for ≥70% of articles; Pinboard `description` fallback confirmed usable
- [x] A valid multi-article XHTML document is written to disk and validates with `lxml.etree.parse()`

### POC Approach

Script fetches 12 real bookmarks from the live Pinboard feed. For each: fetches the article URL, runs `readability-lxml`, applies `lxml` XHTML sanitisation, assesses content quality and title quality, records XML validity. Compiles all successfully-extracted articles into a test XHTML document.

**Spike directory:** `.arness/spikes/spike-001-extraction-xhtml-quality/`

### Result: Validated

The readability-lxml + lxml XHTML sanitisation pipeline works well on real Pinboard bookmarks. All validation criteria met. A 148KB 10-article test XHTML document was written and validated.

### Evidence

| Metric | Expected | Actual |
|--------|----------|--------|
| Good content extraction | ≥80% | 83% overall; 91% of fetchable pages |
| XHTML validity (of fetched pages) | 100% | 100% |
| Good title quality | ≥70% | 92% |
| Test document written + validated | Pass | Pass (148KB, 10 articles) |

Failure breakdown:
- arxiv.org: abstract-only page (39 chars) — expected behaviour, not an extraction bug
- boardgamegeek.com: HTTP 403 — fetch-level failure (UA rejection), not an extraction failure

### Caveats

- Tested on 12 URLs from one user's current feed on one day. Extraction quality may vary over time as bookmark diet changes.
- arxiv.org abstract pages are inherently low-content. The pipeline should log these as low-extraction rather than failures.
- BoardGameGeek returns 403 to the spike UA. Some sites block non-browser requests; the pipeline's per-article failure handling covers this.
- Test document was not transferred to a Kindle device. XHTML validity was confirmed programmatically via `lxml.etree.parse()`.

### Impact on Architecture

No architecture changes needed. The readability-lxml primary + trafilatura fallback + lxml sanitisation design is confirmed.

Title fallback strategy (readability title → Pinboard description) is confirmed useful and should be implemented.

## Spike 002: Pinboard JSON Feed Field Names

### Risk Description

The original architecture assumed the Pinboard JSON feed (`feeds.pinboard.in/json/`) uses field names matching the Pinboard API: `href`, `description`, `time`, `toread`. These had not been verified against the live endpoint.

### Priority

Critical — a parser written against wrong field names fails on every bookmark.

### Validation Criteria

- [x] Feed accessible without authentication
- [ ] Field names confirmed: `href`, `description`, `time`, `toread`
- [x] `toread` flag mechanism confirmed
- [x] `time` field datetime format confirmed
- [x] Top-level structure confirmed (flat array of bookmark objects)

### POC Approach

Script fetches the public Pinboard JSON feed (`/json/u:niksilver/t:toread/`) and pretty-prints the first two bookmarks, then analyses field names, types, and values.

**Spike directory:** `.arness/spikes/spike-002-pinboard-feed-format/`

### Result: Partially Validated

The feed works and returns well-structured JSON, but all field names differ from the assumed schema. Additionally, the decision was made during this spike to switch from the public JSON feed to the private RSS feed (which uses a secret token URL and is the preferred approach).

### Evidence

| Expected field | Actual field | Value type |
|---------------|-------------|------------|
| `href` | `u` | string (URL) |
| `description` | `d` | string |
| `time` | `dt` | string (ISO 8601) |
| `toread` | not present | N/A |

`toread` is not a field — the URL (`t:toread`) pre-filters the feed. Tags are in `t` (list of strings). Additional fields: `n` (notes), `a` (account name).

### Caveats

Moot — the project switched to the RSS feed before implementing the JSON parser.

### Impact on Architecture

The public JSON feed is no longer the target. Replaced by the private RSS feed (Spike 003). No JSON feed parser will be implemented.

### Suggested Alternatives

1. **RSS feed with secret token** (chosen): Use `feeds.pinboard.in/rss/secret:…/u:niksilver/toread/`. Authenticated via URL secret, no API key management, stdlib XML parsing sufficient. Validated in Spike 003.

## Spike 003: Pinboard RSS Feed Format and Parsability

### Risk Description

Following the Spike 002 finding, the project switched to the private Pinboard RSS feed. This feed's format, field names, and parsability with stdlib tools had not been tested.

### Priority

Critical — the feed is the primary data source; parser must be written correctly.

### Validation Criteria

- [x] RSS feed accessible at the secret URL (HTTP 200)
- [x] Parseable with stdlib `xml.etree.ElementTree`
- [x] Each item has accessible article URL, title, and publication timestamp
- [x] Timestamp parseable with stdlib `datetime.fromisoformat()`
- [x] At least one article present in the feed

### POC Approach

Script accepts the feed URL as a CLI argument (secret token not hardcoded). Fetches the feed, detects format, parses with `xml.etree.ElementTree`, prints raw XML of first item, extracts fields from first 5 items, and verifies timestamp parsing.

**Spike directory:** `.arness/spikes/spike-003-pinboard-rss-feed/`

### Result: Validated

All five criteria pass. The feed is RDF/RSS 1.0 (not RSS 2.0), parseable with stdlib `xml.etree.ElementTree` without additional dependencies. 19 items returned. Timestamps are ISO 8601.

### Evidence

```
HTTP 200, Content-Type: application/xml, 23022 bytes
Feed format: RDF/RSS 1.0 (root: {http://www.w3.org/1999/02/22-rdf-syntax-ns#}RDF)
Items in feed: 19

First item raw structure:
<item rdf:about="https://www.theguardian.com/...">
  <title>Effect of 'gamechanger' Alzheimer's drugs 'trivial'...</title>
  <dc:date>2026-04-16T07:34:20+00:00</dc:date>
  <link>https://www.theguardian.com/...</link>
  <dc:creator>niksilver</dc:creator>
  <dc:subject>toread</dc:subject>
</item>

datetime.fromisoformat("2026-04-16T07:34:20+00:00") → 2026-04-16 07:34:20+00:00 ✓
```

Confirmed field paths (namespace-qualified):
- Article URL: `rdf:about` attribute on `<item>`, or `{http://purl.org/rss/1.0/}link` child
- Title: `{http://purl.org/rss/1.0/}title`
- Timestamp: `{http://purl.org/dc/elements/1.1/}date`

### Caveats

- Feed URL contains a private secret token — must be stored in `config.toml` (gitignored), not hardcoded anywhere.
- No article description/summary in feed items. Title, URL, date, and tags only.
- Tested with 19 items; feed size at high bookmark volume is unknown but immaterial (it's an XML response, not paginated).

### Impact on Architecture

The "Feed parsing" layer in the architecture vision must change from `requests + stdlib json` to `requests + stdlib xml.etree.ElementTree` (RDF/RSS 1.0 with namespace-qualified field access). No additional dependencies needed — `lxml` is already present for XHTML sanitisation.

The `config.toml` field `pinboard_feed_url` will hold the full RSS URL including the secret token. This is already gitignored.

The fetcher's `fetch_feed()` method must:
1. Use namespace constants for RDF/RSS 1.0
2. Extract items via `{http://purl.org/rss/1.0/}item`
3. Get URL from `rdf:about` attribute
4. Get title from `{http://purl.org/rss/1.0/}title`
5. Get timestamp from `{http://purl.org/dc/elements/1.1/}date`
